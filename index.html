⚠ The Problem

Why today's rental pricing falls short

Fixed rules and basic comparable matching leave significant value on the table — and lock local expertise inside individual analysts' heads.

🏫

Missing Location Intelligence

School ratings, road noise, flood risk, walkability, and nearby amenities are ignored entirely — even though they can shift rent by 10–25%.

📏

Rigid Rule-Based Logic

Fixed formulas can't adapt to up-and-coming neighbourhoods, seasonal demand, or micro-market dynamics that experienced analysts spot intuitively.

🔄

No Feedback Loop

When analysts override prices, those signals vanish. There is no system to capture, store, and learn from the human judgement being applied daily.

⏱

Slow & Inconsistent

Manual research across multiple data sources takes 20–40 minutes per property. Different analysts produce different prices for identical properties.

✨ The Solution

How RentIQ works at a glance

A three-layer system: real location data, AI reasoning, and a human feedback loop — all connected in one analyst workflow.

📍

Real Location Intelligence

GPS → live OpenStreetMap data → real school counts, noise indicators, flood proximity, park density, and walkability for any property anywhere in the world.

🤖

Claude AI Reasoning

Claude analyses enriched comparables and produces a recommended price, confidence score, and plain-English reasoning — all in the analyst's local currency.

💬

Natural Language Feedback

Analysts give feedback in plain English ("remove noisy ones", "better schools here"). Claude parses it into actions, updates the price, and stores learnings.

🗺 User Journey

From property input to accepted price

A typical analyst session takes under 3 minutes. Here's the complete flow.

1

Property Input

The analyst opens RentIQ and enters the subject property. Address autocomplete (powered by Nominatim) suggests real nearby streets as they type, biased toward their current GPS location. Fields auto-fill: city, postcode, country, and currency.

GPS Detection Address Autocomplete Auto Currency
2

AI Analysis (≈15 seconds)

The backend fetches real nearby streets via Overpass API, derives location signals (schools, noise, flood risk, walkability) from live OSM data, generates 6 comparable properties with realistic local pricing, then calls Claude to produce the recommendation.

Overpass API Location Signals Claude claude-opus-4-6
3

Review Price & Comparables

The analyst sees the recommended price with confidence score, a clear range, and Claude's reasoning. Each comparable card shows the full location factor breakdown — school rating, noise level, flood risk, parks, walkability, and shops — as colour-coded chips.

Price + Range Confidence Score AI Reasoning Location Chips
4

Manual Adjustments

The analyst can remove any comparable with one click (price recalculates immediately) or adjust its influence weight using a slider (0.1× to 2.0×). Every change triggers a fresh Claude analysis on the updated comparable set.

Remove Comparable Adjust Weight Instant Re-price
5

Natural Language Feedback

The analyst types free-form feedback. Claude parses it into structured actions (remove, reweight, note) and immediately updates the price. Pre-built suggestion chips accelerate common scenarios. All exchanges are shown in a chat history panel.

NL Parsing Chat History Quick Prompts
6

Accept & Learnings Stored

The analyst accepts the final price. All feedback text, adjustments made, and resulting price changes are stored in the learnings log — forming a dataset for future prompt improvements, model fine-tuning, and location data corrections.

Learnings Log Future Fine-tuning Audit Trail

🤖 AI Architecture

How Claude powers the pricing engine

Claude plays three distinct roles — initial pricing, feedback parsing, and continuous re-analysis — each with a carefully engineered prompt.

Role 1 · Initial Pricing Analysis

When: On every property submission (and after every adjustment).

Claude receives structured JSON: the subject property, 6 enriched comparable properties with their location factors, and the local currency. It returns a JSON object with recommended price, range, confidence (0–1), and 2–3 sentences of reasoning.

Role 2 · Feedback Parsing

When: On every natural language feedback submission.

Claude receives the analyst's free text plus a summary of current comparables (with their noise/school/flood values). It returns a structured JSON with an acknowledgment sentence and an array of typed actions to apply.

Role 3 · Deterministic Application

When: After Claude returns adjustments.

Claude does not mutate state directly. The backend applies each action mechanically (remove ID from session, set weight float, store note). This makes the system fully auditable — every price change is traceable to a logged action.

# Role 2: Feedback parsing prompt structure system = """ You are a real estate pricing assistant. Parse analyst feedback into structured JSON: { "acknowledgment": "1 sentence response", "adjustments": [ { "action": "remove_comparable" | "adjust_weight" | "note_factor" | "update_learned_weight", "comparable_ids": ["geo_a1b2c3"], "factor": "noise_level", "direction": "increase" | "decrease", "reasoning": "why this was applied" } ] } Interpret analyst language: - "noisy" → noise_level=loud → remove_comparable - "flood risk" → flood_risk≥medium → remove - "better schools" → update_learned_weight school↑ - "up-and-coming" → note_factor (stored for learning) """ user = f""" Comparables: {json.dumps(comp_summary)} Feedback: "{analyst_text}" """ # Actions applied deterministically after Claude responds for adj in parsed["adjustments"]: if adj["action"] == "remove_comparable": session_store.remove_comparable(session_id, adj["comparable_ids"]) elif adj["action"] == "adjust_weight": session_store.set_weight(session_id, comp_id, w) # Always re-run full analysis with updated comparables updated_price = pricing_service.recalculate(session_id)

Confidence Score Calibration

Claude is explicitly instructed to lower confidence when:
• Fewer than 3 comparables remain after removals
• Price variance across comparables is high (>30%)
• Subject property has unusual characteristics
• Location factors contradict comparable signals

⚡ Short-term: Per-session weights

Within a session, learned weights persist (e.g. school_weight: 1.3). If an analyst repeatedly emphasises schools, the session automatically upweights school-rated comparables for that property.

📈 Medium-term: Fine-tuning dataset

Each (property input, feedback text, price delta) triple is a training example. Collected over weeks, these can fine-tune Claude's pricing prompt or train a lightweight regression model for base price estimation.

🗺 Long-term: Location data correction

If "noisy" feedback consistently maps to properties on a particular street type, the system can update the noise classification rules for that street type across the entire dataset.

👥 Team knowledge: Analyst patterns

If analyst X always removes flood-risk comparables, their profile can pre-filter those. If the team consensus is that school rating matters more than walkability, global weights update automatically.

🚀 Production Roadmap

Path from prototype to production

Three phases to transform this prototype into a production-grade pricing platform.

1

Phase 1 — Real Data Integration (4–6 weeks)

Replace mock comparable generation with real property database queries (internal PMS/CRM). Integrate Ofsted, Environment Agency flood maps, and OS noise data for authoritative signals. Add Redis session store. Wire in Rightmove/Zoopla/Rentcast API for transaction-based price anchoring.

PMS Integration Ofsted API Flood Maps API Redis Sessions Transaction Data
2

Phase 2 — Production Hardening (3–4 weeks)

Add user authentication (SSO/SAML), role-based access (analyst vs admin vs read-only), full audit logging of every Claude call, response caching for repeated postcode lookups, and Claude response streaming for sub-second perceived latency.

Auth / SSO RBAC Audit Log Response Cache Streaming
3

Phase 3 — Learning Loop Automation (6–8 weeks)

Build the learnings pipeline: quality-gate feedback events, export to fine-tuning dataset, scheduled prompt evaluation against held-out properties. Implement analyst preference profiles (auto-apply known preferences on login). Add a map view showing comparable locations with heatmap overlays.

Fine-tuning Pipeline Analyst Profiles Map View Heatmaps Prompt Evaluation
